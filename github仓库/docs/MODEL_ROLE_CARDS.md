# 六个模型的岗位卡：按任务分工，而非品牌崇拜

> 本文是工作流设计建议，不是对任何模型的永久排名。模型版本、产品入口、工具权限和价格会变化；每次实验都应记录实际模型标识、日期和能力边界。

## 先区分三个层次

1. **模型/产品**：GPT、Claude、Gemini、Grok、DeepSeek。
2. **执行入口**：网页聊天、API、IDE、CLI、Agent 应用。入口决定能否读写项目、浏览网页、调用浏览器或生成媒体。
3. **工作权限**：只分析、可以改文件、可以运行命令、可以浏览器操作、可以生成资产。不要因为模型“很强”就默认它有这些权限。

## 推荐岗位卡

### GPT / ChatGPT — 产品分析与提示词架构师

**适合承担**：需求澄清、把宽泛目标拆成可验收目标、整理设计 brief、发现冲突约束、组织决策记录。

**输入**：用户目标、产品事实、技术限制、参考截图、现有需求文档。

**输出**：`brief.md`、`design-brief.md` 或结构化决策记录。

**验收**：事实/假设/未知项明确分开；成功标准可观察；未凭空添加业务数据；提示词包含目标、上下文、步骤、输出、验收、停止条件。

**不要默认**：普通 ChatGPT 对话能直接修改本地仓库或运行浏览器。只有在当前入口明确提供相应连接/工具时才能如此描述。

### Codex — 主力实现代理 / 工程执行者

**适合承担**：检查代码库、按 brief 修改项目、运行项目命令、修复缺陷、报告代码差异与测试证据。

**输入**：`brief.md`、`design-brief.md`、现有仓库、明确权限与不可改动范围。

**输出**：真实代码改动、运行说明、diff 摘要、测试结果、截图执行说明。

**验收**：实际查看修改；运行已有构建/lint/test；如有浏览器能力则获取真实截图；严格区分 PASS、FAIL、NOT RUN。

**不要默认**：它已加载某个 Skill、已能访问所有外部 API，或已执行未展示的测试。先查目录、工具与日志。

### Claude / Claude Code — 深度需求分析或独立评审

**适合承担**：复杂约束分析、独立设计批评、代码审查、重构计划。Claude Code 的文件与命令能力以本地安装、权限和项目配置为准。

**输入**：做设计评审时优先只给 `design-brief.md` 和截图；做代码审查时提供 diff、测试结果和需求。

**输出**：`review.md` 或 `code-review.md`，每条意见带证据、严重度、影响和最小修复建议。

**验收**：不会只说“更现代/更好看”；能指出具体位置和可复现问题；将事实缺陷与主观审美分开。

**关键纪律**：独立视觉评审时，不要先把实现者的自我解释和分数喂给评审者。

### Gemini — 多模态观察与素材评估

**适合承担**：分析截图、对比多个视口、检查图像内容与裁切、辅助理解多模态材料。API、Gemini 网页端与 Gemini CLI 的工具能力并不相同。

**输入**：原始截图、目标视口、设计 brief、资产候选图及其用途。

**输出**：截图观察清单、视觉差异、资产适用性意见、`review.md`。

**验收**：每条视觉意见指出截图区域；无法从图像判断的交互必须标记为未知；不把推测写成产品事实。

### Grok / xAI — 创意发散与反主流质疑

**适合承担**：挑战过于常见的方案、提出不同视觉隐喻、指出设计方向的陈词滥调、生成反方评审问题。

**输入**：简短的用户任务、设计 brief、现有 2–3 个方向及明确的差异性目标。

**输出**：独立备选方向、风险清单、最强反对意见。

**验收**：不是为了“酷”而酷；每个新奇元素要说明其用户价值、成本、风险；避免只是换颜色或添加装饰。

### DeepSeek — 结构化分析、代码复核与低成本辅助

**适合承担**：检查设计 brief 是否自洽、审核代码 diff、生成测试用例、将长报告转换成结构化清单。实际能力取决于当前模型、上下文与工具入口。

**输入**：需求、代码 diff、失败日志、测试门槛或 handoff JSON。

**输出**：优先级缺陷列表、测试矩阵、结构化结果。

**验收**：每个缺陷必须可定位；代码建议需能解释原因；JSON 需通过解析；不能把未运行的测试说成通过。

## 最小协作组合

初期建议只用：
- 一个规划/设计 brief 角色（可以由 GPT 或 Claude 承担）；
- 一个主力实现工具（Codex 或 Claude Code）；
- 一个独立评审角色（可用 Gemini、Claude 或另一个独立会话）；
- 人类负责方向选择和最终验收。

Grok 与 DeepSeek 可作为补充角色，不需要每次都调用。是否值得多模型协作，应该由效果、延迟、成本与风险决定。

## 角色选择记录模板

每次实验写下：模型准确名称/版本、入口、启用工具、是否可读写文件、是否能执行命令、是否能查看截图、成本/延迟、输入数据风险，以及为何选择它承担该岗位。
