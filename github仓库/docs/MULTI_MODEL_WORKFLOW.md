# 多模型协作工作流

## 先区分模型和工具入口

GPT、Claude、Gemini、Grok、DeepSeek 是模型/产品家族；Codex、Claude Code、Gemini CLI 是特定的编码或代理工具。网页聊天、CLI、API 的权限不同。一份 `SKILL.md` 不会自动让所有产品具备文件访问、浏览器、图像生成或命令执行能力。

## 推荐岗位分配

| 岗位 | 可由谁承担 | 主要输入 | 主要输出 | 验收方式 |
|---|---|---|---|---|
| 产品/需求分析 | GPT、Claude、Gemini | 用户目标、产品资料 | 问题定义、成功标准、限制 | 人类确认事实和优先级 |
| 创意探索 | GPT、Claude、Gemini、Grok | 产品 brief、随机 seed | 3 个结构不同的方向 | 方案之间存在真实差异 |
| 设计总监/选择者 | 人类，模型辅助 | 候选方向、取舍说明 | 选定方向、反对意见 | 符合产品和用户目标 |
| 主力实现 | Codex 或 Claude Code 等 | 设计 brief、代码库 | 可运行页面、代码差异 | 构建、交互、浏览器检查 |
| 图像/视频资产 | 具备相应工具/API 的模型 | 资产 brief、尺寸、用途 | 图片/视频及使用说明 | 来源、质量、裁切、性能检查 |
| 独立视觉评审 | 与实现者不同的模型/会话 | 截图、brief、评审 rubric | 按严重度排序的问题 | 每项问题有证据和位置 |
| 代码/测试审查 | Codex、Claude Code、DeepSeek 等 | diff、测试结果、需求 | 缺陷列表、测试建议 | 可复现且对应具体代码 |
| 最终验收 | 人类 + 自动化检查 | 页面、截图、测试、报告 | 发布决定 | 明确通过、失败或未验证 |

这是一套可调整的岗位设计，不是对模型永久能力排名。应根据当前工具、成本、延迟、数据政策和任务结果调整。

## 文件交接协议

每个阶段必须产生可被下游独立理解的文件：
- `brief.md`：目标、用户、主要任务、成功标准和限制
- `directions.md`：候选方向、差异、利弊和推荐理由
- `design-brief.md`：最终方向、排版、颜色、素材、交互、反模式
- `asset-manifest.md`：资产文件、用途、来源、尺寸、许可与替代方案
- `review.md`：问题、证据、严重度、建议、置信度
- `qa-report.md`：构建、测试、视口、交互、可访问性和未解决问题
- `decision-log.md`：人类做出的决定与理由

不要只通过长聊天记录交接；将重要决定落到项目文件中。

## 建议状态机

`INTAKE → EXPLORE → HUMAN_SELECT → DEFINE → BUILD → CAPTURE → REVIEW → REFINE → QA → ACCEPTED`

任何阶段失败时都要记录失败原因。不得把未执行的步骤报告为通过。缺少权限、密钥或工具时输出明确阻塞项；需求存在重大歧义时先询问，不要静默猜测。

## 模型调用策略

- 不需要多模型就不要多模型。
- 先用一个主力编码代理完成闭环。
- 将独立评审交给另一个会话或模型，以减少实现者自我辩护。
- 只有当图像/视频能提高理解、品牌识别或关键状态表达时才生成。
- API 密钥放在环境变量或密钥管理器中，不要写入仓库、前端代码或截图。
- 调用外部模型前确认数据政策、费用和是否允许发送项目资料。

## 最低验收门槛

1. 页面实际运行，不只是生成源码。
2. 桌面与移动端截图均已生成，或明确说明为什么不能。
3. 主要交互可操作。
4. 没有已知的严重遮挡、溢出或控制台错误。
5. 键盘焦点、对比度和核心状态已检查。
6. 未解决的问题如实列出。
