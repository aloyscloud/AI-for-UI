# 接入与验证：按部就班完成第一次端到端实验

## 第 0 步：先把来源与工作区整理好

1. 查看 `SOURCES.md` 并校准每个来源链接。
2. 打开第三方 Skill 仓库，查看 LICENSE、NOTICE、文件内容和最新版本。
3. 没有明确许可时，不复制整份 Skill；保留链接并独立编写自己的规则。
4. 建一个实验分支，避免一开始直接改 `main`。

## 第 1 步：选择一项真实任务

任务不要太大。推荐一个包含标题、价值主张、一个主 CTA、三项功能说明和页脚的产品 Landing Page。

约束尽量固定：相同文案、相同需求、相同技术栈、相同视口、相同时间预算。这样才能比较是否是工作流带来的改变。

## 第 2 步：准备最小工具链

需要的最少工具是：
- 一个能够修改项目的编码代理；
- 项目已有的本地运行命令；
- 一个能截图的浏览器或截图工具；
- `brief.md`、`design-brief.md`、`review.md`、`qa-report.md` 这些可留档的文件。

先不要为“多模型”而接入所有 API。API 接入增加密钥、费用、错误处理和隐私风险，应当在单模型闭环跑通后再做。

## 第 3 步：在仓库本地启用 Skill 或提示词

### Codex / 其他编码代理

Skill 目录结构和自动发现规则可能随产品版本改变。不要猜路径：
1. 阅读当前工具的官方 Skill/Agent 文档；
2. 选择它明确支持的项目级或用户级目录；
3. 放入 `SKILL.md` 与所有被引用的相对路径文件；
4. 在工具中列出已发现技能或明确调用技能；
5. 用一次只读任务确认它真的加载了文件，再启动写入任务。

### 普通网页聊天

普通聊天可能没有项目文件和命令执行权限。可以先将所需的 brief、提示词和截图作为上下文提供给模型，让它输出分析建议，再由具备项目权限的编码工具执行。

### API

API 不是“把 API key 填入提示词”。实现时需单独配置环境变量、选择当前官方支持的模型标识、写请求/响应处理、超时和错误处理，并记录调用元数据。不要把密钥写进源码、前端变量或 Git 历史。

## 第 4 步：先做单模型闭环

1. 运行 `prompts/01-intake-and-brief.md`，得到 `brief.md`。
2. 运行 `prompts/02-explore-directions.md`，得到 `directions.md`。
3. 人类明确选定方向和反馈。
4. 运行 `prompts/03-design-brief.md`，得到 `design-brief.md`。
5. 使用 `prompts/04-build.md` 实现页面。
6. 本地实际启动页面，保存桌面与移动端截图。
7. 用 `prompts/05-independent-review.md` 做独立评审。
8. 用 `prompts/06-refine-and-qa.md` 修复并验证。
9. 将结果写入 `experiments/template/experiment.md` 的副本。

## 第 5 步：再增加第二模型

第二模型先只负责一个边界清楚的任务：独立评审截图或审查 diff。不要让两个代理同时改同一个工作树，否则容易出现相互覆盖和无法归因的改动。

交接时必须传文件，而不是“请看看上面的聊天”。至少传 `design-brief.md`、截图路径、评审 rubric 和当前 commit。

## 第 6 步：如果要接 API

- 使用各提供商当前官方文档确认 endpoint、模型 ID、结构化输出和多模态参数。
- 将 key 放入环境变量或密钥管理器；确认 `.env` 在 `.gitignore` 中。
- 为请求记录 provider、model_id、任务 ID、耗时、状态和 token/费用数据（如果接口提供）。
- 为超时、速率限制、无效 JSON、内容拒绝和服务错误设计明确失败路径。
- API smoke test 仅证明文本请求成功，不证明浏览器、图像、视频或代码执行链路成功。

## 第 7 步：用对照实验验证 Skill

比较 A 组（不用 Skill）与 B 组（使用 Skill）。尽量保持输入、模型、时间预算、视口和验收方法一致。隐藏组别后由人评分，另外记录客观缺陷。

建议指标：
- 主要用户任务是否清楚；
- 视觉层级和阅读顺序；
- 与其他方案的结构差异；
- 响应式缺陷数；
- 主要交互通过率；
- 无障碍问题数；
- 实际耗时与费用；
- 需要人类返工的次数。

只有当证据足以支持时，才写“这个 Skill 提升了某方面表现”。不要只比较 AI 的自评分数。

## 第 8 步：发布前检查

- [ ] 来源与许可证说明准确
- [ ] 没有密钥或个人隐私
- [ ] 运行命令和测试记录真实
- [ ] 截图对应当前 commit
- [ ] 没有把待验证项标记为通过
- [ ] 文档区分来源观点、个人判断与原创实验
